An Azure bill that had quietly grown by six figures

Cloud cost reduction for a global accountancy training organisation.

£150,000a year removed from the Azure bill
Hundredsof orphaned resources deleted

The problem

Spend had grown faster than anyone could explain. Nobody owned the bill end to end, several third parties had built into the estate over the years, and the finance question ("why is this going up?") had no technical answer.

What we did

Started with people rather than dashboards: interviewed the third parties and the internal team to find out what was actually in use and what nobody would miss. Then moved virtual machines onto reserved instances where the usage pattern justified it, applied savings plans to app services, and removed hundreds of orphaned resources that were still being paid for.

Where it landed

A recurring saving of £150,000 a year, and a cost picture the team could keep current themselves.

What to take from this

  • Most cloud overspend is not inefficiency, it is abandoned work nobody has permission to delete.
  • Interviews find more savings than tooling does, because the tooling cannot tell you what is no longer needed.
  • Reserved instances only pay off where the usage pattern is genuinely stable. Buy them for the wrong workload and you have just prepaid for waste.
  • A saving that nobody can maintain comes back within a year. Leave the team the workbook.

A streaming platform nobody left in the building could explain

Taking over, diagnosing and re-platforming a system we did not build.

70%lower total cost of ownership over three years
Hours to minutesCI build times after pipeline work

The problem

A self-hosted video streaming platform, built by people who had moved on, with no current architecture documentation and no reliable account of how it was deployed. It was slow under load and nobody could say which part was the bottleneck.

What we did

Reverse-engineered the microservice architecture and the build and deploy process from scratch, then audited the infrastructure for real capacity rather than assumed capacity. Load tested with K6 to find where it actually broke, which turned out to be mis-tuned NGINX, an under-spec'd RabbitMQ and badly sized components in both directions. Restructured the services to remove the bottlenecks, replaced an inherited Puppet codebase with Ansible playbooks, and moved the platform from on-premise to autoscaling Azure defined in Terraform.

Where it landed

A platform that scales with demand, a 70% reduction in total cost of ownership measured over three years, and CI pipelines that finish in minutes rather than hours.

What to take from this

  • Load test before you re-architect. Over-provisioned components hide the real limit as effectively as under-provisioned ones.
  • "It needs more servers" is usually wrong. On this platform the binding constraint was configuration, not capacity.
  • Inheriting a system is a research job first and an engineering job second. Budget for the reading.
  • Lifting a badly understood system into the cloud unchanged just moves the bill. Fix the bottlenecks first, then move it.

A private AI platform for documents that cannot leave the building

Self-hosted inference and RAG for a global professional education body.

Zerothird-party inference APIs in the data path
One per use caseisolated platform and private vector store

The problem

Real demand for retrieval over internal documents, and an absolute constraint that those documents could not be sent to a third-party model API. Several separate use cases, each with its own sensitivity, which could not be allowed to see each other's data.

What we did

Built GPU-accelerated Azure infrastructure defined in Terraform and Ansible, running self-hosted inference on vLLM, Ollama and llama.cpp. Added a document ingestion pipeline, vector storage on Postgres with pgvector plus Chroma and LanceDB, Redis for caching and RabbitMQ for message handling, behind a clustered NGINX reverse proxy. Built the API layer and a React chat front end with single sign-on and a configuration page. Every use case runs on its own isolated platform with its own dedicated private vector store, so data never crosses between them. Zero trust and least privilege throughout, containerised, automated with GitHub Actions, observable through Grafana.

Where it landed

In production, serving several use cases, with scale handled by adding nodes rather than rebuilding.

What to take from this

  • "We cannot use the API models" is a platform problem, not a reason to abandon the use case.
  • Isolation per use case costs more than one shared index and is usually the only answer that survives a security review.
  • Self-hosted inference is an infrastructure project wearing an AI hat. Most of the work is GPU capacity, networking and identity.
  • Put the configuration in a page someone else can operate, or you become the dependency.
