Give every AI use case its own vector store

James Dettmer, Principal 4 November 2026 3 min read

One shared index is cheaper, simpler and the thing most likely to fail a security review. Here is why we build it the expensive way.

We built a private LLM and retrieval platform for a global professional education body. The hard constraint was absolute: internal documents could not be sent to a third-party model API. That part is well understood, and it is an infrastructure problem rather than an AI one.

The less obvious constraint was the one that shaped the architecture. There were several separate use cases, each with its own sensitivity, and they could not be allowed to see each other's data.

The cheap design, and why it fails

The straightforward way to build retrieval over a document set is one index, with metadata on each chunk saying which collection it came from, and a filter applied at query time. It is efficient, it is simple to operate, and almost every tutorial you will read describes it.

It also means that the only thing standing between a finance document and an HR query is a WHERE clause. One bug in filter construction, one prompt that manipulates how a query is assembled, one developer debugging with the filter temporarily removed, and data crosses a boundary it was never supposed to cross.

That is a hard thing to defend in a security review and an impossible thing to prove. "The filter is always applied" is a statement about the code as it is today, not about the system.

What we built instead

Each use case runs on its own isolated platform with its own dedicated private vector store. Not a separate index inside one store. A separate store. Data does not cross between use cases because there is no path along which it could.

Around that sits the rest of it: GPU-accelerated Azure infrastructure defined in Terraform and Ansible, self-hosted inference on vLLM, Ollama and llama.cpp, a document ingestion pipeline, Postgres with pgvector alongside Chroma and LanceDB, Redis for caching, RabbitMQ for message handling, a clustered NGINX reverse proxy, and a React chat front end with single sign-on. Zero trust and least privilege throughout, containerised, automated with GitHub Actions and observable through Grafana.

The objection, and the answer

The objection is cost, and it is a fair one. Per-use-case isolation means more infrastructure, more to operate and more to pay for.

The answer is that the comparison is not isolation against a shared index. It is isolation against not being allowed to run the use case at all. In a regulated or document-sensitive organisation, the shared-index design frequently does not survive review, and the project dies at the point where it needed sign-off rather than at the point where it needed engineering.

Scale is handled by adding nodes, which is a cost conversation rather than a rebuild.

The wider point

Self-hosted inference is an infrastructure project wearing an AI hat. Most of the work is GPU capacity, networking, identity and ingestion. The model is the part everybody talks about and the part that takes the least time.

And put the configuration somewhere a person other than you can operate it. We built a configuration page with content safety settings for exactly that reason. If the only way to change a prompt or a safety threshold is to ask the people who built it, you have not delivered a platform, you have delivered a dependency.

Questions this usually raises

Does isolation mean duplicating the documents?

Only where the same document genuinely belongs to more than one use case, which is rarer than people expect. Usually the collections are naturally distinct, and where they overlap it is a deliberate decision rather than an accident of indexing.

Could you not just use separate namespaces?

You can, and it is better than filters. It is still one system with one set of credentials and one blast radius. Whether that is sufficient depends on who has to sign it off, which is why the question belongs in the design conversation rather than the build.
