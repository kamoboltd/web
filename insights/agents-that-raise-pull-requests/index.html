Agents should raise pull requests, not push code

James Dettmer, Principal 4 November 2026 3 min read

The difference between an agent that is useful and an agent nobody will let near production is almost always the approval gate.

We build and operate a suite of autonomous AI agents running unattended in production on a live online platform with more than 18,000 registered users and over 500 daily actives. They answer user support queries, monitor server logs and surface incidents, and review code and raise fixes.

They raise those fixes as pull requests. A human approves every merge. No agent pushes code directly, and that is not a transitional safety measure we intend to remove later.

Why the gate is the design, not a restriction on it

An agent that can open a pull request can do almost everything useful an agent can do in a codebase. It can read the repository, reproduce a bug, write a fix, write a test, explain its reasoning and put the whole thing somewhere a person can look at it.

What it cannot do is be wrong at three in the morning without anyone noticing. That is the entire difference, and it costs you the time it takes someone to read a diff.

It also changes the conversation with whoever has to approve the system. "An AI will change our production code" is a hard sell in most organisations and an impossible one in some. "An AI will do the legwork and raise a pull request like any other contributor" is a conversation about code review, which every engineering team already knows how to have.

What it takes to run unattended

The agents are built on the Anthropic Claude SDK and Claude CLI, with BullMQ for task queuing, retries and priorities, and Postgres with pgvector as the knowledge store. The parts that matter for reliability are the unglamorous ones:

  • Error handling, because an agent that fails silently is worse than no agent
  • Retries with priorities, so a transient API failure does not drop a support query
  • Logging throughout, so you can reconstruct what it did and why
  • Approval gates at every point where an action is consequential

Most of the engineering in a production agent is queueing, state and observability. The model call is a small part of it.

Where the gate belongs for other kinds of agent

Support agents can answer and resolve a great deal autonomously, because the blast radius of a wrong answer is a confused user and an escalation. The gate belongs at actions that change account state or cost money.

Operations agents can watch logs, diagnose and write up an incident continuously. The gate belongs at remediation, and it should be a different gate depending on whether the remediation is restarting a worker or changing a configuration.

We also built an enterprise agent inside Microsoft Teams on the same stack, which is the right shape when the people who need it already live in Teams and will not adopt another interface.

A test worth applying

Before you ship an agent, ask what it would cost if it were confidently wrong ten times in a row overnight. If the answer is survivable, it can run unattended. If it is not, there is a gate missing, and finding it is cheaper now than after.

Questions this usually raises

Does the approval gate not remove most of the value?

It removes the part of the value that nobody responsible will accept anyway. Reproducing a bug, writing a fix and preparing a reviewable change is most of the work; approving a good diff takes a couple of minutes.

What stops the agent raising dozens of poor pull requests?

Priorities and queueing, mainly. The agent works a queue rather than reacting to everything, and anything it cannot do well goes to a human as a write-up instead of as a change.
