Load test before you re-architect

James Dettmer, Principal 4 November 2026 2 min read

Over-provisioned components hide the real limit as effectively as under-provisioned ones. Until you have measured, you are guessing which.

We were asked to take over a self-hosted video streaming platform. It had been built by people who had moved on. There was no current architecture documentation and no reliable account of how it was deployed. It was slow under load and nobody could say which part was the bottleneck.

The instinct in that situation, and the thing the budget is usually already pointed at, is to re-architect. Break up the monolith, add nodes, move to managed services, buy bigger instances. All of which may eventually be right, and none of which you can justify yet.

What the load testing found

We ran extensive load testing with K6 against the real system, looking for where it actually broke rather than where we assumed it would. The causes were:

  • NGINX mis-tuned, so the ingress gave up well before the services behind it did
  • RabbitMQ under-spec'd, so message handling became the ceiling under concurrency
  • Redis in need of tuning
  • Components provisioned badly in both directions, some well over what they needed and some well under

That last point is the one worth sitting with. Over-provisioning is usually discussed as a cost problem, and it is. It is also a diagnostic problem, because a component with far more headroom than it needs will never show up in your metrics as a constraint, and it will mask whatever sits behind it. You end up tuning the thing that is visibly struggling while the actual limit is somewhere quieter.

"It needs more servers" is usually wrong

On this platform the binding constraint was configuration, not capacity. More servers would have cost more and moved the ceiling very little, because the ceiling was a worker count and a connection limit, not a shortage of compute.

This is the common case rather than the exception. Systems that are slow under load are far more often badly configured than genuinely out of resource, and configuration is cheaper to fix than architecture is to change.

Then, and only then, move it

Once the bottlenecks were out, the platform was restructured to remove them properly and moved from on-premise to autoscaling Azure defined in Terraform. That produced a 70% reduction in what it cost to run, measured over three years.

Note the order. Had we lifted the platform into the cloud first, which is what the original brief pointed at, we would have paid cloud prices for the same mis-tuned NGINX and the same under-spec'd queue, and then autoscaled the symptoms. Lifting a badly understood system into the cloud unchanged does not fix it. It just moves the bill and gives you a more expensive version of the same problem.

What this costs

Load testing an unfamiliar system is a few days, not a few weeks, and it is almost always cheaper than the architecture change it either justifies or prevents. If it justifies the change, you now have evidence to take to whoever is funding it. If it prevents one, you have saved considerably more than the test cost.

Questions this usually raises

What do you need access to in order to load test?

A representative environment and permission to push it until it breaks. Production is possible with care and out of hours, but a sized-alike environment is better, because the interesting part is finding the limit rather than respecting it.

How is this different from an APM tool?

Application performance monitoring tells you what is happening at current load. Load testing tells you what happens at loads you have not reached yet, which is the question people are usually actually asking.
